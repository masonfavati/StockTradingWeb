# StockTradingWeb Project Constitution

## 1. Engineering principles
- Develop on feature branches, never directly on main.
- Keep changes focused, reviewable, and tested.
- Do not merge failing tests, linting, typing, or builds.
- Update documentation when behavior or interfaces change.

## 2. Technology
- Backend: Python 3.14+, FastAPI, SQLAlchemy 2, Alembic,
  PostgreSQL, Pydantic v2, uv, pytest, Ruff, and mypy.
- Frontend: Node.js 24, pnpm, React, TypeScript strict,
  Vite, Tailwind CSS v4, React Router, and TanStack Query.
- Frontend quality: Vitest, Oxlint, and production builds.

## 3. Financial correctness
- Use Decimal/NUMERIC for money and share quantities.
- Explicitly define currencies, price precision, and rounding.
- Record transaction fees and relevant corporate actions.
- Never invent prices, returns, or model performance.
- Label delayed, simulated, and live data accurately.

## 4. Statistical integrity
- Prevent look-ahead bias and training/test leakage.
- Use time-ordered validation and out-of-sample evaluation.
- Account for transaction costs, slippage, and liquidity.
- Compare predictions against simple investment benchmarks.
- Preserve prediction timestamps, model versions, and inputs.
- Report uncertainty and risk, not guaranteed future prices.
- Permit a NO TRADE recommendation.
- Compare investment horizons using documented,
  defensible risk-adjusted objectives.

## 5. Trading safety
- No automatic real-money trades in the initial product.
- Simulated trading must be clearly distinguished from reality.
- Never display hypothetical profits as realized profits.
- Do not describe estimated peaks as guaranteed sell prices.

## 6. Security
- Never commit credentials, API keys, or personal financial data.
- Keep account data isolated between users.
- Validate inputs and enforce authorization on the server.
- Use environment variables for configuration.
- Follow least-privilege principles.

## 7. Database rules
- All schema changes require Alembic migrations.
- Review autogenerated migrations before applying them.
- Do not delete user data silently.
- Test financial constraints and transaction calculations.

## 8. Acceptance requirements
- Backend tests, Ruff, and mypy must pass.
- Frontend tests, linting, and build must pass.
- Database migrations must apply successfully.
- Features require meaningful acceptance tests.
- Pull requests must describe changes, tests, and limitations.

## 9. Product development
- Build foundational capabilities before predictive features.
- Validate forecasts before presenting recommendations.
- Do not expand into high-frequency trading without
  suitable market data and evidence of model reliability.
- Maintain an auditable record of model evaluations.

## 10. Change control
Changes to these governing rules require an explicit,
documented decision. Unresolved product decisions must
not be silently assumed.
